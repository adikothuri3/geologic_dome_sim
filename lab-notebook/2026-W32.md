## Sun Aug 2 — Phase 1 done, on Windows instead of WSL2

Demo: `phase1_stand.mp4` — G1 posed through stand → crouch → stand → t-pose → arms-up →
stand on a numpy-generated heightfield, orbiting camera, 471 frames / 18.8 s at 25 fps.
Contact sheet in `reports/phase1_contact_sheet.png`.

### What broke, in order

**1. `wsl --install` did nothing.** Looked like a hang. It wasn't — no `wsl`, `dism` or
installer process existed at all, `LxssManager` was never registered, nothing WSL-related
was staged for reboot. Root cause: `VirtualizationFirmwareEnabled = False`. **AMD SVM is
disabled in the BIOS** and Gigabyte ships B550 boards that way. No OS-side fix exists on
consumer Gigabyte boards — they expose no WMI BIOS provider the way Dell/Lenovo/HP business
machines do. Needs a physical trip to firmware: `shutdown /r /fw /t 0` → Tweaker → Advanced
CPU Settings → SVM Mode → Enabled.

Lesson: "stuck" is worth five minutes of process-list checking before waiting on it. Nothing
was running.

**2. Pivoted to native Windows.** Phase 1 turned out to need none of WSL: MuJoCo physics is
CPU, and Windows rendered through WGL with `MUJOCO_GL` unset on the first try — no EGL/OSMesa
fight at all, which was the risk I'd been most worried about. The whole environment was up in
about ten minutes.

**3. `git clone` failed TLS.** `unable to get local issuer certificate`. Already documented in
`notes/setup.md` from the skills install — global git config pins OpenSSL and fails against
GitHub on this box. `GIT_CONFIG_*` + `http.sslBackend=schannel` fixed it. The vault paid for
itself here; I'd have burned 20 minutes rediscovering that.

**4. `mediapy` needs a system ffmpeg.** Fine on Linux, absent on Windows. Swapped to
`imageio` + `imageio-ffmpeg`, which bundles its own binary — one code path for both OSes now.

**5. Duplicate keyframe name.** Declared my own `stand` key in the scene while `g1.xml`
already had one → `repeated name 'stand' in key`. Mine was a verbatim copy anyway, so I
deleted it and inherited Menagerie's. One fact, one home, even in XML.

**6. Meshes not found (the fiddly one).** `<include>`ing `g1.xml` from `sim/` broke every
mesh path. `g1.xml` declares `meshdir="assets"`, and MuJoCo resolves that relative to the
**top-level** scene file, not to the included file — Menagerie's own `scene.xml` never hits
this because it sits beside `g1.xml`. Two false starts before I stopped theorising and wrote
a probe script trying five configurations. Answer: our `<compiler>` must come **after** the
`<include>` (MJCF applies elements in order, so putting it first lets `g1.xml`'s own meshdir
win), with `meshdir` relative to `sim/`.

Also learned the error message names a *random* missing mesh each run — MuJoCo loads meshes
in parallel. I briefly read that as "progress" between attempts. It wasn't.

**7. Sphere drop test failed, and the test was wrong.** Three of four probes reported "still
moving." The spheres were **rolling downhill** — MuJoCo models sliding friction, not rolling
resistance, so a sphere never settles on a 4° slope. The one that passed was the flat spawn
pad, which should have been the tell. Switched the probe to a box. The `mjcf-terrain` skill
says "sphere/box"; for sloped terrain it has to be a box.

Worth noting the heights matched `sample_height` to within a centimetre even while failing —
that's the row/col orientation empirically confirmed, which is what Phase 4 actually needs.

**8. The robot fell — on the last transition only.** Held stand, crouch, stand, t-pose,
arms-up all at 0.0 cm drift, then toppled going arms-up → stand. Swinging both arms down
1.8 rad in one second dumps angular momentum into a floating base with straight legs and no
ankle strategy to absorb it. Not a terrain problem. Fixed with a slew-rate limit on the
position targets (`MAX_JOINT_RATE = 0.8 rad/s`, so that blend stretches to 2.25 s) plus
smoothstep easing so the rate is zero at both ends.

This is the most useful thing I learned all day: **position actuators hold joint angles, not
balance.** Phase 1 gets away with posing only because the spawn pad is level. Everything a
policy is for starts exactly here.

**9. Terrain looked flat on camera.** Demo passed all assertions, but 6 cm of relief over a
6 m field is invisible at a downward camera angle — and my own verification criterion said
"visibly non-flat terrain." Raised `elevation_z` to 0.15 m and dropped the camera to −8°
so relief reads in silhouette against the sky. Passing assertions ≠ a good demo.

### Experiment: `FLAT_PAD_FRAC = 0` — what the pad is actually holding up

Ran the demo with the level spawn pad disabled, to see the boundary rather than assume it.
Evidence: `reports/phase1_fall.png` (the topple), `reports/phase1_fall_poses.png` (after).

It fell in **under a second**, during the 1 s settle, before the pose sequence even started:

```
settled: pelvis 0.383 m above terrain        # with the pad: 0.792 m
stand  held 2.0s  clearance 0.081 m  drift 26.2 cm
```

Spawned on ~10° of slope, straight legs locked, CoM outside the support polygon. No recovery
mechanism exists, so there was no recovery.

**The result worth keeping** is what the log said *after* it fell:

```
crouch   held 1.5s  clearance 0.101 m  drift 0.0 cm
t_pose   held 1.5s  clearance 0.073 m  drift 0.0 cm
arms_up  held 1.5s  clearance 0.085 m  drift 0.0 cm
```

**0.0 cm drift — perfect joint tracking — while flat on its back.** All 29 actuators held
their commanded angles to a fraction of a degree the whole time. `kp=500` knows exactly one
thing: joint error. It does not know about gravity, base orientation, or contact. The robot
performed a crisp t-pose in the dirt and reported success.

Two consequences:

- **The `never collapsed` assertion is load-bearing, not decoration.** Judging this run by
  tracking error alone would have scored it a pass. Any Phase 5 eval harness needs a base
  height/orientation term that is *independent* of joint tracking, or a fallen policy looks
  good on the metrics that are easiest to log.
- **~10° of slope is not mild** for a straight-legged stand — I'd assumed it was. The pad is a
  bigger crutch than the slope statistics suggested.

This is now the baseline for Phase 2: a policy standing unaided with `FLAT_PAD_FRAC = 0` is a
real before/after, and the failing video exists to compare against.
