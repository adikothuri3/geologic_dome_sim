# Decision log

Append-only. Every entry: the choice, the reasoning, and the rejected alternative. Newest at the bottom. Entries are never edited — if a decision is reversed, append a new entry that supersedes it.

---

## 2026-08-01 — Streaming reconstruction with LingBot-Map, not offline COLMAP

**Choice:** LingBot-Map (streaming, monocular RGB) as the reconstruction engine.
**Why:** The trek is one long continuous walk — exactly the long-streaming regime LingBot-Map was built for (stable past 10,000 frames, ~20 FPS, leads Oxford Spires / Tanks & Temples / ETH3D). It needs no LiDAR or depth camera, which matches what Pemba actually carries, and enables same-day turnaround during the expedition window.
**Rejected:** COLMAP-style offline SfM — it's the baseline being beaten; an offline batch run can't support the daily [[runbook]] cadence and struggles at trek-length sequences.

## 2026-08-01 — Stand on MuJoCo Playground's G1 environment, don't build locomotion from scratch

**Choice:** Fine-tune the existing Playground G1 joystick-locomotion environment (MJX) rather than writing a G1 RL environment from zero.
**Why:** Playground's G1 env has demonstrated sim-to-real transfer; the project's novelty is the terrain loop, not the locomotion baseline. Time budget is ~12–15 hrs/week with hard expedition deadlines.
**Rejected:** Custom environment from scratch (months of reward-shaping work that already exists), and Isaac-family GPU simulators (MuJoCo's contact dynamics are more realistic for legged contact, and MJX still gives the GPU parallelism).

## 2026-08-01 — Two terrain paths, heightfield first

**Choice:** Build both conversion paths, in order: `hfield` heightfield first, static collision mesh second (see [[pipeline]] for parameters).
**Why:** Heightfields are fast, robust, and sufficient for most walking terrain; meshes are only *needed* for overhangs and big boulders, and cost more (Poisson reconstruction, decimation, contact tuning).
**Rejected:** Mesh-only (slower, fragile contacts for the common case) and heightfield-only (can't represent overhangs at all).

## 2026-08-01 — WSL2 Ubuntu 24.04 as the dev environment

**Choice:** WSL2 + Ubuntu 24.04 on the Windows 11 box (see [[setup]]).
**Why:** JAX-CUDA, which MJX requires, doesn't run natively on Windows, and DimOS targets Linux.
**Rejected:** Native Windows (blocked by JAX-CUDA); native Ubuntu dual-boot (acknowledged as better, deferred for setup speed — revisit if WSL2 GPU passthrough causes pain).

## 2026-08-01 — Default posture: sim-validated recommendations, not mid-expedition redeployment

**Choice:** Frame Phase 7 output as sim-validated recommendations plus sim2sim evidence; redeploying policies onto Pemba mid-expedition happens only if expedition leads green-light it.
**Why:** The G1 policy stack is partly closed (Unitree's factory controller ≠ our policy) and hardware risk decisions belong to expedition leads. Daily 3D reconstructions + terrain-difficulty analytics are already a first-of-kind contribution even without the closed loop.
**Rejected:** Committing to closed-loop redeployment as the success criterion.

## 2026-08-01 — Documentation split: vault for state, lab notebook for history

**Choice:** This vault (`notes/`) holds only current, distilled documentation; the weekly lab notebook lives in `lab-notebook/` outside the vault; git holds history (stale vault content is deleted, not appended).
**Why:** The vault's one job is giving an agent or human enough context to work on the pipeline in <5 min per note. Journaling inside it would rot that guarantee.
**Rejected:** One combined PKM-style vault with daily notes.

## 2026-08-02 — Menagerie `unitree_g1` as the asset source

**Choice:** Build on `mujoco_menagerie/unitree_g1` (`g1.xml`, 29 position actuators, `nq=36`, one `stand` keyframe).
**Why:** It is the canonical, officially maintained G1. Menagerie also ships `g1_mjx.xml` / `scene_mjx.xml` with `home` and `knees_bent` keyframes, so Phase 2's MJX work can stay in the same repo — choosing Menagerie costs nothing downstream.
**Rejected:** Playground's `g1_mjx_feetonly.xml` as the asset. Same robot with feet-only collision geoms, but it lives inside the Playground tree and would split our asset source across two repos for no Phase 1 gain. This settles the *asset* only — the 2026-08-01 decision to fine-tune Playground's G1 joystick *environment* rather than write one from scratch is unchanged.

## 2026-08-02 — Phase 1 built on native Windows; WSL2 deferred to Phase 2

**Choice:** Run Phase 1 (load → keyframe posing → heightfield → render) natively on Windows. WSL2 remains the Phase 2+ environment; this scopes the 2026-08-01 WSL2 decision rather than reversing it.
**Why:** `wsl --install` is hard-blocked — AMD SVM is disabled in the B550's firmware and cannot be changed from the OS (see [[setup]]). Phase 1 needs no GPU, no JAX and no hypervisor: MuJoCo physics is CPU and Windows renders through WGL with `MUJOCO_GL` unset. Waiting on a BIOS trip would have idled a whole phase for nothing; the demo landed the same day instead.
**Rejected:** Blocking Phase 1 on the BIOS fix. Also rejected: making Windows the permanent environment — JAX-CUDA still does not run natively there and DimOS targets Linux, so MJX training genuinely needs WSL2 before Aug 16.

## 2026-08-02 — `imageio` for video, not `mediapy`

**Choice:** Write frames with `imageio` + `imageio-ffmpeg`.
**Why:** `mediapy` shells out to a system `ffmpeg` binary, which exists after `apt install` on Linux but not on Windows. `imageio-ffmpeg` ships its own binary as a wheel, so one code path covers both OSes — which matters because this project will keep straddling them.
**Rejected:** `mediapy` plus a manual ffmpeg install on Windows (an extra install step and a PATH dependency, for no benefit).

## 2026-08-03 — DimOS gets its own venv, isolated from the Phase 2 environment

**Choice:** `--phase6` installs `dimos[base,unitree]` into `~/venvs/dimos`, not the shared `~/venvs/dome` that MJX training uses.
**Why:** DimOS resolves ~289 packages, including torch, a second full CUDA stack, and its own numpy pin. Installing that alongside jax/MJX lets a Phase 6 dependency silently re-resolve numpy or a CUDA library underneath the locomotion policy. Phase 2 is due Aug 16 and Phase 6 not until Sept 27 — a working training environment is worth far more right now than import convenience later, and the two only need to exchange terrain files, not live objects.
**Rejected:** One shared venv (simplest, but stakes a working Phase 2 on a Phase 6 dependency resolution); deferring DimOS entirely (leaves an unknown install risk sitting in front of a September deadline).

## 2026-08-03 — Allocate VRAM on demand, not by preallocation

**Choice:** Set `XLA_PYTHON_CLIENT_PREALLOCATE=false` in `check_phase2.py` and `train_g1.py` before JAX initialises its GPU backend.
**Why:** This 4060 Ti also drives the Windows desktop, which holds ~2 GB. JAX's default 75 % preallocation asks for 6.0 GiB of 8 GiB, fails outright, and falls back down a retry ladder to a fragmented pool. On-demand allocation leaves the display its share and makes `num_envs` the single honest lever for VRAM (see [[setup]]).
**Rejected:** Tuning `XLA_PYTHON_CLIENT_MEM_FRACTION` to a fixed slice — it hardcodes an assumption about what the desktop is using, which changes every time VS Code or a browser opens. Also rejected: leaving the default and living with the retry ladder, which works but starts every run fragmented.

## 2026-08-03 — Pin `jax[cuda12]==0.9.2` until brax catches up

**Choice:** Pin jax to 0.9.2 in `scripts/setup_wsl.sh` rather than tracking latest.
**Why:** brax 0.14.2 — the newest release, and what Playground requires — still calls `jax.device_put_replicated` in `ppo/train.py:756` and three other places. jax deprecated that in 0.8.1 and **removed** it in 0.10.0 as part of the `pmap` → `jit(shard_map)` migration, so an unpinned install resolves to 0.11.0 and every PPO run dies at startup. brax declares only `jax>=0.4.6`, so nothing upstream prevents the bad resolution. 0.9.2 is the last release with the API; MJX, Warp and the G1 env all verified working on it, with `--smoke` reaching reward −3.07.
**Rejected:** Shimming `device_put_replicated` ourselves — the drop-in needs explicit sharding, and hand-rolling device placement under brax's PPO to dodge a version pin is a poor trade. Also rejected: pinning jax without pinning down *why*, which is how a pin outlives its reason — unpin when brax ships a fix, and re-verify with `train_g1.py --smoke`.

## 2026-08-04 — One robot: Menagerie `unitree_g1` plus our own configs, nothing else

**Choice:** Every simulated G1 in this project is Menagerie's `unitree_g1` geometry — meshes, kinematics, inertials — with our own MJCF on top. No second robot source, no vendor URDF import, no hand-modelled links.
**Why:** A real2sim2real pipeline is only as trustworthy as the claim that the sim robot *is* the real robot. One source makes that claim checkable in a line: if it isn't in `mujoco_menagerie/unitree_g1/assets`, it isn't the robot. This is already true in practice and is now a rule — Playground's `g1_mjx_feetonly.xml` references Menagerie's STLs directly (`../../../../../mujoco_menagerie/unitree_g1/assets/*.STL`), so its G1 and our Phase 1 G1 are the same machine; Playground only wraps it with MJX-friendly collision primitives, sensors and actuators. Our additions live in `sim/` and are generated, not hand-drawn: `scripts/make_full_collision_xml.py` sizes every collision box from the Menagerie mesh it wraps, so the collision volume cannot drift from the real geometry.
**Rejected:** Importing Unitree's own URDF (a second, divergent source of truth for the same robot); hand-authoring collision capsules (fast to write, impossible to verify, and drifts silently when upstream updates); and using Menagerie's `type="mesh"` collision geoms verbatim, which are the highest-fidelity option but are convex-mesh collisions that make GPU training impractically slow — see the full-collision entry below.

## 2026-08-04 — Full-body collision, with primitives derived from the meshes

**Choice:** Train on a G1 where every link can touch the world, not just the feet. `scripts/make_full_collision_xml.py` generates `sim/g1_full_collision.xml`; `scripts/check_full_collision.py` gates it; `train_g1.py --full-collision` trains it.
**Why:** Playground collides feet only — fast and adequate on a flat plane, and wrong for this project. On reconstructed Everest terrain a shin, knee, hip or torso meeting rock is a real event, and a policy that has never felt one has a blind spot the simulator never showed it. Generating each primitive from its body's Menagerie mesh bounding box means the collision volume follows the real robot instead of hand-guessed capsules. The gate caught two faults that would otherwise have been invisible: upstream's `left_thigh` and `left_shin` capsules interpenetrate by 16 mm at the nominal pose (harmless while nothing collides, a robot-toppling force once broadphase is on), and the shin capsules are radius 0.08 — a 16 cm-thick shin — which grazes the floor while merely standing and would have poisoned `feet_slip`, `feet_air_time` and the contact sensors with phantom ground contact.
**Consequence worth knowing:** enabling collision also revives `left_foot_right_shin_found` / `right_foot_left_shin_found`. Those sensors are read by `_get_termination()` to catch leg crossing, but their contact `<pair>`s are commented out upstream, so that half of the termination test could never fire in the feet-only baseline.
**Rejected:** Menagerie's mesh collision geoms (highest fidelity; convex-mesh collision is far too slow for 200M GPU steps — revisit for a low-env-count Phase 5 validation run). Also rejected: hand-placing capsules, where one wrong offset gives a robot resting on invisible geometry and the render looks fine.

## 2026-08-05 — Reconstruct into our own export, and only trust one window

**Choice:** `recon/reconstruct.py` wraps LingBot-Map's model API rather than calling upstream's `demo.py`, writes `cloud.ply` + `trajectory.npz` + `run.json` itself, and — until cross-window alignment is fixed — clips are sized to fit a **single window** (~124 frames at `window_size 24`, `keyframe_interval 6`).
**Why:** `demo.py` exports nothing; it runs inference and opens a viser viewer, so closing the tab discards the reconstruction. Phase 4 needs a cloud and a camera trajectory on disk, so an export layer has to exist somewhere and owning it lets us record the run config, VRAM peak and alignment diagnostics in the same place. The single-window rule is empirical, not cautious: stitched runs produced camera paths **34–38×** the scene extent with a hard pose jump at a window boundary, and tripling the overlap made it worse — the failure is scale estimation on low-texture overlap, not overlap size. The same clip in one window lands at 2.8×. `run.json` records `traj_length_over_extent` so the check is automatic rather than remembered.
**Why not just use their viewer:** we still do — `recon/view_viser.py` serves the *exported* files, so any past run reopens in seconds without a GPU, instead of re-running inference to look at a result.
**Rejected:** `demo_render/batch_demo.py --save_predictions`, which does export, but pulls in kaolin plus a CUDA extension build for a rendering path we don't need. Also rejected: accepting the stitched full-clip cloud as the deliverable — it is visibly wrong, and shipping a broken artefact into Phase 4 would surface as mysterious terrain geometry three weeks later.
**Corrected 2026-08-05:** this entry originally also rejected streaming mode "because it holds every frame on the GPU." That was our bug, not the model's behaviour — streaming slices per frame exactly as windowed does, and runs the full clip at flat 5.63 GB. The single-window rule survives the correction, but for a different reason than first written: the limit is ~25 s of footage per consistent scene in *either* mode, set by drift once the scene leaves the KV cache's memory horizon, not by window stitching alone. See [[setup]].

## 2026-08-05 — LingBot-Map gets its own venv

**Choice:** `scripts/setup_lingbot.sh` installs into `~/venvs/lingbot`, not the shared `~/venvs/dome`.
**Why:** Upstream pins torch 2.8.0/cu128; `~/venvs/dome` holds the `jax==0.9.2` pin that brax needs. One venv means two CUDA stacks negotiating over the same numpy, and a Phase 3 install could silently break the Phase 2 training environment. Same reasoning as the DimOS venv above, and it cost nothing — the two exchange PLY files, not live objects.
**Consequence:** the viewer needs viser *and* Open3D, which live in different venvs; viser was added to `~/venvs/dome` (the one with Open3D) rather than Open3D to the recon venv, to keep the working inference environment untouched.

## 2026-08-07 — Pivot the primary simulator to Isaac Sim / Isaac Lab; MuJoCo becomes working legacy

**Choice:** From Phase 4 on, the primary simulator is **Isaac Sim 5.1.0 + Isaac Lab 2.3.x** (Python 3.11, pip install, native Windows 11 — no WSL), with RSL-RL for training. All MuJoCo/MJX/Playground code moves to `sims/mujoco/` and stays runnable; Phases 1–2 stand as delivered, and vanilla MuJoCo keeps the 50 Hz sim2sim-validation role in the pipeline's stage 7. This **supersedes the 2026-08-01 entry** that rejected "Isaac-family GPU simulators."
**Why:** the Robot Everest team's actual stack is Isaac — their research doc's open-source track reads "Mapping the full Everest route using Lingbot-Map into IsaacSim, with domain randomization over snow, ice friction, and wind gust … dedicated RL locomotion policies on the route twin." MuJoCo was the onboarding stand-in, and this onboarding is meant to mirror the real deal. The 2026-08-01 entry's reasons were real (MuJoCo's contact fidelity, MJX parallelism) but matching the team's deliverable outweighs them — and Isaac brings its own leverage: built-in **full-collision `G1_CFG`** (what Phase 2 had to build by hand), ready-made `Isaac-Velocity-Flat/Rough-G1-v0` tasks, `unitreerobotics/unitree_rl_lab`, USD terrain import (`MeshConverter`, OBJ/STL/FBX), procedural terrain generation as a LingBot fallback, and `EventManager` domain randomization (friction/ice, mass, pushes as wind-gust proxy). A second forcing factor: LingBot-Map has been unreliable on this box (kvsw ≈ 24 ceiling, ~25 s drift horizon), so terrain now comes from LingBot **only if it works**, else stock/procedural mountain terrain — Isaac's generator makes that fallback first-class.
**Compute:** this box (8 GB VRAM, 16 GB RAM) is below Isaac's official minimum (16/32). Local = headless smoke tests at 64–256 envs; real training on a rented cloud GPU. That split is the documented Isaac-community pattern, not an improvisation.
**Rejected:** staying on MuJoCo (diverges from the team's route twin — the thing this onboarding exists to mirror); maintaining both sims as equal first-class tracks (double upkeep on a solo repo; MuJoCo instead keeps one job, sim2sim); Isaac Lab 3.0 beta (Ubuntu-only as of mid-2026); Isaac under WSL (native Windows is supported at these versions and WSL adds nothing but GPU-passthrough risk); deleting the MuJoCo code (it is the Phases 1–2 evidence and the stage-7 validator).
**Consequence:** repo restructured into `sims/isaac/` (primary) + `sims/mujoco/` (legacy) with sim-agnostic `recon/` feeding both; the vendored third-party mujoco skill and its junction removed; `runs/` gains per-sim subdirs (`runs/mujoco/`, `runs/isaac/`) going forward. See [[overview]] for the re-targeted milestones and `sims/isaac/README.md` for the bring-up plan.

## 2026-08-08 — The Isaac velocity task carries our own DR set, because upstream's G1 has none

**Choice:** `Dome-G1FullCollision-Flat-DR-v0` (`sims/isaac/tasks/dome_g1/`) is the Phase-4a training task. It keeps upstream Isaac's rewards and observations untouched — the 2026-08-01 "don't rebuild the locomotion baseline" rule still holds — but replaces the event set wholesale with `DomeG1DREventCfg`, the MuJoCo Phase-2 `domain_randomize` set rebuilt as `EventManager` terms, and corrects the command distribution to the three-channel joystick Phase 2 trained on. The no-DR task is retained as `Dome-G1FullCollision-Flat-v0`, the A/B control.
**Why:** the 2026-08-07 pivot entry lists "`EventManager` domain randomization" among Isaac's built-in leverage. That is true of Isaac Lab in general and **false of its G1 config specifically**: `G1RoughEnvCfg.__post_init__` sets `push_robot = None`, `add_base_mass = None`, `base_com = None`, zeroes the reset velocities, pins the joint-reset scale to `(1.0, 1.0)`, and collapses the physics-material ranges to point values (static `0.8→0.8`, dynamic `0.6→0.6`). What survives in stock `Isaac-Velocity-Flat-G1-v0` is observation noise and nothing else. Taking the pivot entry at face value would have shipped a Phase-4a policy trained on one fixed robot and called it domain-randomized — and since the terrain track's whole point is snow and ice friction, that is the one thing that must not be assumed.
**Why a separate task rather than a flag:** so "does this randomize anything" is answerable by reading a task id. The failure mode here is silent — a task that randomizes nothing trains, logs and plots exactly like one that does — so the answer must not live inside a boolean three inheritance levels down.
**Why gate C:** `check_isaac.py --gate c` measures each term's spread **across environments** out of PhysX (`root_physx_view`, `robot.data.*`) rather than reading the config back. Configuration is not evidence: it caught a `scale` operation applied to a property whose default is `0.0`, which is a no-op that looks identical to working randomization from every angle except this one.
**Rejected:** patching upstream's `EventCfg` in `__post_init__` (the parent chain runs *after* the field is set and dismantles exactly the terms that matter — `push_robot` and the joint-reset range — so the events are assigned last instead); `reset_joints_by_scale` as upstream uses it (17 of the G1's joints default to exactly `0.0` and scaling leaves them untouched; Playground's ±0.05 rad is absolute, so `reset_joints_by_offset` is the faithful term); randomizing joint friction at all (the G1 USD ships `0.0` on all 37 joints and scale cannot lift zero — dropped rather than left in as decoration, with the zero asserted in gate C so a future asset surfaces it); and keeping upstream's `heading_command = True` with `rel_heading_envs = 1.0`, which derives yaw rate from a heading controller in every env so the sampled `ang_vel_z` never reaches the robot — that is a different task from a joystick, and upstream's forward-only `lin_vel_x` `(0, 1)` is a policy that cannot walk backwards.
**Not yet randomized, still Phase 5:** motor strength (`randomize_actuator_gains`), sensor/command latency, terrain variants. See [[locomotion-policy]] for the full term-by-term mapping.

## 2026-08-08 — Long-trail terrain comes from a real survey DEM, not recon or a generator

**Choice:** Phase 4b's long mountain terrain is a **real trail from survey-grade elevation data**: the Eiger Trail (Eigergletscher→Alpiglen, OSM route 353) sampled from swisstopo's free **swissALTI3D 0.5 m DEM**, built by `sims/isaac/terrain/{fetch_eiger_trail,build_trail_terrain,mesh_to_usd}.py` into a straightened 5.4 km × 24 m strip (x = arc length, y = cross-track, z = real elevation; 713 m descent) → OBJ → USD with exact-triangle-mesh collision, consumed by `Dome-G1FullCollision-EigerTrail-v0` (`sims/isaac/tasks/dome_g1/trail_env_cfg.py`).
**Why:** "long" is the one thing reconstruction cannot deliver — LingBot-Map is a per-segment tool (~25 s / ~25 m per consistent scene; the 2026-08-08 A100 sweeps killed every mission-scale config), and procedural terrain is not a real trail. A national DEM has no scale ambiguity, no drift, and no capture session; the 0.5 m grid resolves the trail bench, rock bands and stair sections a G1 actually negotiates. The Eiger Trail specifically because it is the **same terrain family as GrandTour EIG-1** (alpine rock-and-gravel descent in the same massif) — recon benchmarks and the RL terrain now describe the same kind of ground.
**Straightening:** the strip is unrolled along the trail's arc length so env origins and spawning are trivial (grid origins at z = 0, the stock usd-terrain behavior, are meaningless on 713 m of relief — a custom `TerrainImporter.configure_env_origins` loads walkable spawn points instead, filtered to ≤1 m relief over a ±1 m patch because the OSM centerline strays a few metres off the real bench). Elevation profile, cross-slope and steps survive; map-view curvature does not.
**Rejected:** a georeferenced curved corridor (spawn/origin bookkeeping for zero training benefit); Everest-region DEMs (best public grids are ~30 m — macro slope only, no footstep-scale geometry); waiting on LingBot segments (23 m per scene, see above); the procedural generator as the *primary* (it stays as the fallback and the Phase-5 randomization substrate, but it cannot claim "the real trail"); synthesizing micro-roughness below the DEM's 0.5 m resolution (kept honest instead — `meta.json` records `micro_noise: none`; perturbation belongs to Phase 5 terrain randomization, same as for recon terrain).
**Consequence:** `data/` now holds re-fetchable DEM tiles + built terrain (gitignored; the scripts are the provenance), the isaac venv gains `tifffile`+`imagecodecs` (see [[setup]] — pin hazard noted there), and the trail task registers in its own module rather than `dome_g1/__init__.py` so it stays importable standalone.

## 2026-08-08 — Gate the stepping reward on the full command, not just its linear part

**Choice:** `Dome-G1FullCollision-Flat-DR-v0` replaces upstream's `feet_air_time_positive_biped` with `dome_g1/mdp.py::feet_air_time_joystick`, identical except that the "is a step wanted here" gate uses the norm of all three commanded channels rather than `command[:, :2]`. Weight, threshold, single-stance requirement and clamp stay upstream's. This is the **first and only deviation from upstream's reward function** in the project; the 2026-08-01 rule otherwise stands.
**Why:** upstream's gate is right for upstream's task and wrong for ours, and the difference is structural rather than a matter of taste. Upstream runs `heading_command=True` with `rel_heading_envs=1.0`, so its yaw command is a *decaying heading correction* — the robot turns to face a target and the command goes to zero. Yaw is a transient there. We command yaw **directly** (`heading_command=False`) to match the Playground joystick task, which makes yaw a *persistent* command worth the full `track_ang_vel_z_exp` weight of 1.0, forever. With stepping unrewarded for a pure turn, pivoting on the spot collects the entire yaw reward at no cost — no swing phase, and near-zero `action_rate_l2`, which was the dominant term at −0.41.
**The evidence it is real, not theoretical:** run `2026-08-08-isaac-g1fc-flat-dr-4096` (4096 envs, upstream's own sample count and then some). `feet_air_time` sat at **~0.01 from iteration 199 to 1599** and `track_lin_vel_xy_exp` plateaued at **0.37 — what standing still scores — by iteration 200**, while `track_ang_vel_z_exp` climbed steadily 0.37 → 0.62. It converged to "turn, never step" by iteration ~400 and 1,400 further iterations changed nothing. The eval agrees exactly: 0.75 of a commanded 1.0 rad/s yaw, **zero** translation on all three linear commands, 100 % survival throughout.
**Why more compute was not the answer:** this is the second time the Phase-4a sample count was blamed. The first time it was real (256 envs, 16× short — see [[setup]]). This time the curve is flat from iteration 200 onward at upstream's full 4096 envs, which is what distinguishes "undertrained" from "converged to the wrong thing". A flat reward-term curve over 1,400 iterations is the discriminator; mean reward alone is not, since it kept rising on the yaw term.
**Why Playground did not hit this** despite the same direct-yaw joystick commands: its reward carries `feet_phase` (+1.0), a *reference gait clock*, plus `feet_air_time` at +2.0. Isaac's G1 has no gait-phase term at all and compensates by making the task easier via the heading command. Taking Playground's harder command distribution onto Isaac's reward function produced a task harder than either — the deviation here restores the balance at the cheapest point.
**Rejected:** reverting to `heading_command=True` (it would very likely walk, being upstream's proven recipe, but a joystick policy whose yaw you cannot command directly is not the Phase-2 task and is not what DimOS will drive); lowering `action_rate_l2` (it is the dominant penalty, so this would probably also unlock stepping — but the standing complaint about the MuJoCo gait was *jitter*, and action-rate is exactly the term that suppresses it, so buying locomotion by paying in smoothness is the wrong trade here); raising `feet_air_time`'s weight (does nothing on its own — the term is multiplied by a gate that is *zero* for a turn, and 2.0 × 0 is still 0); and more training (ruled out by the flat curve above).

## 2026-08-08 — Track the best checkpoint by reward *terms*, and abort a flat run automatically

**Choice:** the Isaac trainer gains `sims/isaac/scripts/train_guards.py` — an `OnPolicyRunner` subclass overriding `log()` only — which writes `progress.jsonl` (append-only, one line per iteration), `best.json` + `model_best.pt`, and `outcome.json`, and which **aborts the run** if `Episode_Reward/feet_air_time` has not exceeded 0.02 anywhere in the trailing 200 iterations once iteration 500 is passed. The best checkpoint is chosen by `walk_score = track_lin_vel_xy_exp + track_ang_vel_z_exp`, **gated** on `feet_air_time ≥ 0.02`, and never by mean reward.
**Why not mean reward, which is what the MJX trainer used:** because on this task it is actively misleading, and that is measured. Across run `2026-08-08-isaac-g1fc-flat-dr-4096` mean reward rose **−30.4 → +4.11** over 1,792 iterations while `feet_air_time` sat at 0.005–0.010 and `track_lin_vel_xy_exp` stayed pinned at 0.37 — what standing still scores. The entire gain was the yaw term. A `best.json` keyed on mean reward would have confidently named the most thoroughly non-walking checkpoint of the run. The two terms in `walk_score` are the two the failure separated: yaw alone is collectable by pivoting on the spot, so the gate is what makes the score mean "walking" rather than "moving".
**Why best-checkpoint tracking at all:** MJX parity, and the reason there was measured too — brax returns the *final* parameters and both 2026-08-04 runs peaked near 80M steps then drifted down, the full-collision one ending **4.6 below its own peak**. RSL-RL has the same shape of problem: it saves every `save_interval` and the last file written is whatever the run happened to stop on. `"gated": false` in `best.json` is the honesty valve — it marks the best checkpoint of a run that never stepped, so it cannot be mistaken for a policy.
**Why abort automatically:** `sims/isaac/README.md` already carried the criterion ("if it is still flat by iteration ~500, kill it") and it depended on a human watching. Both 4096-env runs were in fact killed externally, and one of them thereby bypassed the trainer's own handler and left **no experiments row at all** for the most important result of that session. A watchdog inside the process both enforces the criterion and guarantees the row.
**Consequence — the exit code is not usable as a signal.** `raise SystemExit(3)` after `simulation_app.close()` was measured to exit **0**: Kit owns process shutdown, the same root cause as `sys.exit("message")` raising `TypeError` inside a running app (2026-08-08 guard-selftest). So the verdict goes in `outcome.json` and any automated driver reads that; a *missing* `outcome.json` is the retryable case, because it means the process never reached its own teardown.
**Rejected:** scraping the TensorBoard event file (couples the guards to a logger backend that is configurable); a separate periodic eval rollout during training (a second env and real wall-clock, to measure what the reward terms already say); rewriting a whole `progress.json` array each iteration (a SIGKILL mid-write loses the file, which is precisely the failure mode being fixed — JSONL survives it); and aborting on the adaptive-KL learning rate pinning at its 1e-5 floor (a real symptom, but too indirect to end a run on — it is recorded per iteration instead).

## 2026-08-08 — A positive control run, and the first Colab notebook for Isaac

**Choice:** `Dome-G1FullCollision-Flat-Heading-v0` — the Phase-4a DR physics with upstream's *task definition* restored (`heading_command=True`, `rel_heading_envs=1.0`, `lin_vel_x` back to (0.0, 1.0), and upstream's linear-gated `feet_air_time_positive_biped`) — trained alongside the two candidate configurations. `colab/isaac_g1_flat_colab.ipynb` runs all three on a Colab L4.
**Why a control is worth a third of the compute:** two full-size runs have failed to produce locomotion and `feet_air_time_joystick` is a *hypothesis* about why. If upstream's own recipe walks on this robot under this randomization, the joystick command distribution is confirmed as what makes the task hard — which is what the 2026-08-08 gate entry claims and has never tested. If it does **not** walk, the fault lies somewhere neither hypothesis reaches (the DR set, the full-collision robot, the harness itself) and both other runs are uninterpretable. That is worth knowing *before* reading a result into them, not after.
**What deliberately does not vary:** `DomeG1DREventCfg` and the raised joint-position observation noise stay identical across all three runs. The variables under test are the command distribution and the stepping gate; anything else moving with them would forfeit the comparison.
**The control is not a candidate policy.** A joystick whose yaw cannot be commanded directly is not the Phase-2 task and is not what DimOS will drive — rejected on those grounds above, and still rejected. Its eval variant turns `heading_command` back *off*, because `play_g1_flat.py` pins all three command channels and a live heading controller would overwrite the yaw channel every step, so the pin would silently not hold.
**Why Colab, given [[setup]] now says 4096 envs fits locally:** three sequential 3000-iteration runs is ~9 h that should not own the dev box, and the eval renderer needs several GB the 8 GB card genuinely does not have — `play_g1_flat.py --video` crashes it at 687 ms. The notebook is therefore the only path on which the *video* deliverable exists at all.
**Rejected:** base64-baking the scripts into the notebook as `colab/lingbot_map_colab.ipynb` does (that predates the repo having a remote; a pinned `git clone` is simpler and cannot go stale); running the three configurations in parallel (they would contend for one GPU and the watchdog makes a dead run cheap anyway); an A100 runtime (NVIDIA lists GPUs without RT cores as unsupported for Isaac Sim 5.1, and the renderer is the part that needs them); and committing the experiments rows from inside Colab (that would move HEAD between runs, so the three rows would name three different commits for the same code).

## 2026-08-08 — The Everest objective terrain comes from NASA's HMA 8 m DEM

**Choice:** the mountain terrain that mirrors the expedition objective is a ~2 km patch of the **real Everest summit pyramid** from the NASA/NSIDC **High Mountain Asia 8 m DEM mosaic** (`HMA_DEM8m_MOS` v1, tile-677 — WorldView/GeoEye stereo, ~1.9 m RMSE validated at Everest), built by `sims/isaac/terrain/{fetch_everest_dem,build_everest_terrain,mesh_to_usd}.py` into `data/everest/terrain/` and consumed by `Dome-G1FullCollision-Everest-v0` (`sims/isaac/tasks/dome_g1/everest_env_cfg.py`). This **supersedes the "Everest-region DEMs" rejection** in the 2026-08-08 long-trail entry above, whose premise — "best public grids are ~30 m" — turned out to be wrong: the HMA mosaics are 8 m and free (Earthdata login).
**Why:** Phase 4b's next terrain must be *the* mountain, and 8 m posting resolves the summit ridge, the faces and the col geometry — macro- and meso-scale route structure — even though it cannot resolve footstep-scale rock. That limitation is recorded, not papered over: `meta.json` carries `micro_noise: none` (void filling is 8-neighbor mean interpolation only, capped at ~48 m reach, abort above 15% voids), and sub-DEM roughness belongs to Phase 5 randomization, same ruling as the Eiger strip. Unlike the Eiger trail there is no centerline: the patch is axis-aligned to the DEM grid (x = east, y = north, centered), so nothing is resampled — the heightfield *is* the cropped grid. Spawn origins are per-cell-slope filtered (≤ 15°, the Eiger ±1 m-relief criterion is sub-cell at 8 m posting and literally uncomputable) with a recorded fallback ladder (relax to 20° → extend toward the South Col flats).
**Rejected:** Sketchfab/TurboSquid Everest meshes (not georeferenced, unknown vertical fidelity); the famous 1984 Swiss 10 m photogrammetric model and Nat Geo's 2021 scans (not publicly downloadable); Copernicus GLO-30 (the "foggy" 30 m grids the original rejection correctly dismissed); synthesizing sub-8 m detail (breaks the honesty rule that makes `meta.json` trustworthy); LingBot recon of expedition footage for this terrain (the ~25 s / ~25 m horizon cannot cover a summit pyramid, and no usable summit footage exists yet).
**Consequence:** downloads need a free NASA Earthdata login — credentials live in `%USERPROFILE%\_netrc` (outside the repo, never committed; see [[setup]]); `data/hma_dem/` holds the re-fetchable 370 MB tile (gitignored, script is provenance); the projection is hand-rolled (no pyproj in the isaac venv) — and it turned out to be the custom **HMA Albers Equal Area** (std parallels 25/47, origin 36 N 85 E, geokey `ProjCoordTrans=11`), *not* UTM as first assumed; the build script asserts the Albers parameters from the geokeys and self-checks by round-trip against the tile's tiepoint.

## 2026-08-09 — Training runs with Kit's RTX renderer disabled outright

**Choice:** `check_isaac.py` and `train_g1_flat.py` both pass `--/app/renderer/enabled=false` to Kit by default (`--keep-renderer` opts out). `play_g1_flat.py` is untouched — `--video` genuinely renders.
**Why:** `--headless` does *not* disable the renderer. `isaaclab.python.headless.kit` still sets `renderer.enabled = "rtx"`; what headless drops is the *viewport* (`AppLauncher._resolve_viewport_settings` sets `_render_viewport = False`), not the RTX subsystem. Training does not draw a single frame between `AppLauncher` and the final checkpoint, so that subsystem was being loaded for nothing.
**Measured, same box, same seed:** gate b at 4096 envs **28,975 → 33,596 env-steps/s** (+16%), gate a startup **~8 s → 6.5 s**, and a 10-iteration smoke whose final mean reward was **−7.21169098127972 both ways** — identical to the last digit. Speed changes; the result does not. That equality is the evidence that this is free rather than a trade.
**The reason it actually matters:** NVIDIA's Isaac Sim 5.1 requirements page states *"GPUs without RT Cores (A100, H100) are not supported"*, and that constrains exactly the subsystem now switched off. With it off there is nothing left on the training path for a datacentre GPU to fail on, which turns "the A100 is unsupported, use an L4" into "the A100 trains, the L4 renders". Cloud GPU choice stops being a constraint on the biggest-ticket item ([[open-questions]] had it open).
**Rejected:** leaving it on and hoping (the failure mode on a no-RT-core card is a *hang*, per IsaacLab #2584 — on Colab that costs the session, not just the run); `renderer=None` via the raw `SimulationApp` dict (this repo uses Isaac Lab's `AppLauncher`, and bypassing it would fork the launch path for one flag); and disabling it in `play_g1_flat.py` too (that script's whole purpose includes rendering an mp4).
